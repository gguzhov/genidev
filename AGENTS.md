# Правила проекта

Этот репозиторий содержит личный сайт Геннадия Гужова. Правила ниже действуют на весь проект.

## Основные принципы

- Перед изменением интерфейса сверяйся с [`docs/design-system.md`](./docs/design-system.md). Визуальные токены, палитру и правила их применения храни там, а не в этом файле.
- Используй только цвета из палитры проекта. Новый цвет добавляй в `docs/design-system.md` лишь тогда, когда существующих токенов объективно недостаточно.
- Сохраняй интерфейс лаконичным, профессиональным и персональным. Приоритеты: ясная иерархия, читабельность, доступность и быстрый доступ к работам и контактам.
- Не добавляй новые библиотеки, зависимости или внешние сервисы без явной необходимости.

## Адаптивная разработка

- Работай по принципу Mobile First: сначала реализуй полноценный сценарий для узкого экрана, затем последовательно расширяй макет. Добавляй breakpoint, когда его требует контент, а не под конкретную модель устройства.
- Проверяй интерфейс на контрольных ширинах:
  - 375 px — основной mobile: одна колонка, без горизонтального скролла страницы, touch targets не меньше 44×44 px;
  - 430 px — широкий mobile: корректные отступы, формы, CTA и длинный контент;
  - 768 px — tablet: навигация, карточки, модалки и переход к многоколоночным секциям;
  - 1024 px — малый desktop/tablet landscape: сетка, боковые зоны и плотность контента;
  - 1280 px — основной desktop: max-width, длина строк, hero-секция и рабочее использование свободного пространства;
  - 1440 px — широкий desktop: контент не должен чрезмерно растягиваться или оставлять случайные пустоты.
- На всех ширинах исключай перекрытия, обрезанный контент, случайные пустоты и неумышленный скролл всей страницы. Для широкого содержимого используй локальный горизонтальный скролл или адаптивное представление.
- Проверяй длинные тексты, загрузку, пустые и ошибочные состояния, экранную клавиатуру, safe-area, keyboard navigation и видимый focus state. Перед завершением исправь responsive-регрессии либо явно укажи, что не удалось проверить.

### Адаптивность текущего лендинга

- На mobile выстраивай hero в порядке: заголовок и обещание, основной CTA, полностью видимый портрет, затем путь работы. Не перекрывай лицо, контактную кнопку или важные части фотографии декоративными плашками.
- Путь работы из шести этапов на ширинах 375–430 px показывай вертикально в одну колонку: «Проблема → Решение → Экономика → Разработка → Запуск → Аналитика». Горизонтальную схему включай только тогда, когда подписи помещаются без наложений и обрезки.
- На mobile отключай pointer tilt и не делай hover обязательным для понимания или управления. Реактивную анимацию заднего визуального слоя включай только для устройств с `hover: hover` и `pointer: fine`; при `prefers-reduced-motion` оставляй композицию статичной.
- Список бизнес-задач может иметь локальный горизонтальный snap-скролл, но не должен перехватывать вертикальный скролл страницы. Выбранная задача обязана оставаться понятной без hover и иметь заметный focus state.
- Для каждой бизнес-задачи показывай четыре действия и четыре результата. На 375 px результаты складывай в одну колонку, а переход к двум и более колонкам делай только когда полный текст помещается без обрезки и горизонтального скролла страницы.
- Карьерная линия на mobile строится в одну колонку без чередования сторон.
- Полноэкранные кейсы учитывают safe-area, имеют внутренний скролл и заметную кнопку закрытия не меньше 44×44 px.
- Карточки проектов используют одинаковую геометрию медиа 3:2 на всех ширинах. Логотип продукта и реальный интерфейс должны оставаться читаемыми поверх декоративного фона; карточка обязана открываться нажатием и с клавиатуры, без зависимости от hover.
- На mobile карточка проекта показывает не больше четырёх сильнейших подтверждённых результатов; плашки переносятся целиком и не образуют горизонтальный overflow.
- Перед завершением отдельно проверяй на 375 и 430 px: видимость лица и CTA в hero, отсутствие пересечений шестишагового пути, полные тексты четырёх результатов, читаемость логотипов и отсутствие горизонтального скролла страницы.

## Интерфейс и доступность

- Для интерфейсных иконок по умолчанию используй Hugeicons и официальный пакет библиотеки для выбранного стека.
- Для логотипов компаний, продуктов и сервисов используй актуальные официальные SVG, предпочтительно из The SVG. Не рисуй приблизительные версии логотипов.
- Иконки без видимой подписи должны иметь доступное имя; декоративные иконки скрывай от assistive technologies.
- Используй семантическую HTML-разметку, достаточный цветовой контраст, управление с клавиатуры и заметный `focus-visible`.
- Уважай пользовательскую настройку `prefers-reduced-motion`.

## MCP и инструменты

- Источник MCP-конфигурации — настройки клиента Codex. Не дублируй MCP-конфигурацию в проекте, плагинах или кэшах.
- Подключай MCP и skills только по контекстной необходимости или прямому запросу.
- Никогда не сохраняй ключи, токены и другие секреты в коде, документации, аргументах команд, патчах или логах.

## Проверка результата

- Перед завершением запускай доступные проверки проекта: форматирование, lint, typecheck, тесты и production build.
- После изменений интерфейса проверяй ключевые страницы на всех контрольных ширинах и исправляй responsive-регрессии.
- Не изменяй и не удаляй пользовательские правки, не относящиеся к текущей задаче.
